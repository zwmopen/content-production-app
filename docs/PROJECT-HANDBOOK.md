# 团建工作台项目手册与持续检查清单

> 这份手册是开发、热更新、真实生产测试和交付前 review 的共同入口。新增需求先登记，再实现，再验证；没有通过的项目不能标记为完成。

## 0.14.18 回归规则

- 切换账号窗口必须先读取该窗口自己的 quota snapshot，再更新助手；禁止显示上一个账号的数据。
- 连续模式只有页面/桥接暂时故障自动重试；上传冲突、低产出、解析不确定和真实限额必须暂停等待探测。
- 用户暂停/停止必须取消对应窗口 retry timer；重新启动后从队列检查点继续，不清理登录分区。

## 0.14.17 账号窗口恢复与等待循环

- 每个账号窗口都必须保存自己的阶段、任务、附件确认数、生图数、暂停/停止状态和下一次探测时间；切换窗口只恢复对应检查点。
- “暂停”只停在安全检查点；“停止”才终止该窗口本轮自动运行。两者都不能删除队列、配置或登录分区。
- 单账号单模板（等待循环+手动窗口）只处理当前选中的账号窗口；单账号单模板（等待循环+自动窗口）在真实额度/低产出信号后切换下一个账号窗口。
- 额度首次探测按本轮第一次上传/生图起点计算；探测失败后 10–20 分钟自动重试。网页真实限额优先，本地估算不得硬阻止手动继续。
- 上传确认后立即更新小猫 `x/y`，轮询阶段更新实际生图数；不会等到迁移计划才显示上传状态。

## 0.14.16 素材使用次数目录规则

- 新归档只允许写入素材库根目录下的纯数字目录：`1`、`2`、`3`、`4`……，数字就是该帖子成功使用次数。
- `0` 次素材不额外建立数字目录；未使用素材继续留在原分类目录或用户手动目录中。
- `已使用一次`、`已上传 2 次`、`已制作三次GPT` 等历史目录继续兼容识别，但不再新建；归档时会按识别到的次数加一并落到数字目录。
- 归档前先取元数据账本次数与物理路径次数的较大值再加一，避免旧账本为 0 时把 `1` 次素材错误留在 `1`。

## 0.14.13 缓存维护与网页触顶规则

- 每套素材任务只有在图片、TXT、成品目录真实落盘后才刷新对应 GPT 账号窗口；刷新不重建账号分区。
- 固定每 3 小时执行一次临时缓存维护：只允许 `session.clearCache()` 和忽略缓存刷新；严禁在该路径调用 `clearStorageData()`，不得删除 Cookie、localStorage、登录态、扩展数据或生产记录。
- 生产任务正在上传、等待计划、出图、请求文案、下载或打包时，维护到期必须顺延，不能因为清缓存刷新打断当前帖子。
- 出图上下文遇到“出了点问题，请重试”等通用提示时，只有同时排除网络、离线、超时、验证码和登录异常，才作为候选触顶/降级信号；记录阶段并暂停，不继续盲目发送下一帖。
- 维护失败必须可见、可重试且不改变队列；登录分区数据保护是更高优先级。

## 当前工作原则

- 开发版优先热更新；不删除 Chromium/GPT/Google 登录分区、缓存、账号窗口、用户配置或生产记录。
- 一次只让一个账号窗口处理一个帖子。当前帖子未完成、跳过或安全暂停前，不允许向该窗口注入下一帖。
- 真实网页状态优先于本地额度估算。遇到验证码、验证、限流、脚本输出或低图数异常，暂停当前帖子，记录原因，等待下一次探测。
- 手动和自动只区分触发者，下载、TXT、查重、打包、归档必须走同一条本地工作包链路。
- 失败不伪造完成：缺 TXT、图片不足、下载不完整或成品目录不存在时，不归档素材、不显示成功。
- 手动上传只把真实帖子附件放进 GPT，不改写输入框；“网页脚本”、下载器、扣 1、下载和打包属于系统状态机，不属于用户素材提示词。只有自动模式才注入最小的会话母版提示。
- 账号窗口不是 GPT 外面的第二个浏览器：顶部标签切换持久账号窗口，底部复用该窗口的单一网页容器；默认是 ChatGPT，地址栏可访问其他普通 `http/https` 网页，返回首页即可回到 ChatGPT。

## 生产模式口径（0.14.12）

1. **手动模式**：选择帖子后只处理用户主动触发的当前队列。
2. **自动模式**：按当前选择的帖子启动一次自动闭环，不自动跨周期补充。
3. **永不停歇模式**：在工作时间内按使用次数从低到高补充帖子，完成一帖后再取下一帖；触顶后按本轮探测时间等待。
4. **单窗口多浏览器轮换模式**：每个账号窗口仍然一次只处理一帖；同一窗口连续处理，只有网页真实限额、低产出或降级信号才切到下一个可用窗口。切换不会改变已启动任务绑定的账号，也不会重传已送达的帖子。

轮换模式的硬规则：成功不是轮换条件，真实网页信号才是轮换条件；所有账号窗口均不可用时暂停并保存 `runId`、当前账号、阻塞账号和 `nextProbeAt`，恢复后先试最早可探测窗口。

## 6 个生产模式（0.14.28）

1. **人工控制（manual）**：选择一个帖子，上传到当前账号窗口；后续发送、复制、下载或打包由用户操作。
2. **选材后自动（automatic）**：按当前选择的帖子启动一次自动闭环，严格逐帖串行；不自动跨周期补充新素材。
3. **单账号全自动（single）**：绑定当前账号窗口和当前会话模板；一个帖子完成后才继续下一个，按使用次数从低到高选择素材；触顶后按本轮探测时间等待。
4. **定时单账号全自动（scheduled）**：在 single 基础上增加定时窗口（默认 07:00-02:00）；非工作时段不领取新任务。
5. **多账号全自动（rotate）**：每个账号窗口有独立队列、会话、额度组和检查点；每个窗口仍然一次只处理一个帖子，互不串号；触顶切换到下一个可用账号。
6. **单账号多对话巡检（patrol）**：实验模式，默认关闭；遍历账号历史对话，按对话状态补齐未完成的步骤。

每个模式都支持右键"修改模式设置、重命名、删除配置（确认）"。模式配置至少包括：

- 继续当前会话 / 注入模板提示词；
- 自动确认文字；
- 文案请求词；
- 阶段超时、最低图片数、自动复制/下载/打包/归档；
- 工作时间、定时启动、并行账号窗口数和账号绑定。

## GPT 状态机检查

当前会话状态必须能落到以下之一：

`ready → uploading → waiting-plan → plan-ready → waiting-images → images-ready → waiting-copy → copy-ready → packaging → archived → completed`

必须检查：

- 侧边栏/当前会话是否包含“模板”或已绑定模板；不符合时不得盲目注入。
- 计划正文稳定后 1–5 秒内只发送一次确认文字；计划未完成不得发送。
- 生成图绑定当前回复；脚本/Python/压缩包输出、重试或限额信号立即停止当前帖子。
- 图片和 TXT 都完成后才能打包；生成 1–3 张时按低图数异常处理，不请求文案、不打包、不归档。
- 已完成或已失败的检查点恢复时，不重复上传、确认、文案请求或归档。
- 输入框残留的自动草稿可清理；用户无关草稿仍是硬边界，不覆盖。

## 当前唯一优先级：单账号自动串行闭环

在这条链路真实稳定前，多账号和多窗口只保留已有代码，不继续扩展。

用户操作只有两步：

1. 在素材树勾选一个帖子文件夹，或勾选一个合集父文件夹；父文件夹会展开为多个独立帖子任务。
2. 选择“单账号单模板·永不停歇”，点击开始生产。

系统必须严格逐帖执行：

`上传当前帖子 → 等待迁移计划稳定 → 发送一次 1 → 等待完整图片 → 请求小红书文案 → 等待文案稳定 → 保存 TXT → 下载当前回复图片 → 统一工作包打包 → 校验成品 → 素材归档 → 下一帖`

硬边界：

- 父文件夹只是批量选取入口，不能把多个帖子合并为一次上传。
- 当前帖子未完成、失败跳过或真实限额暂停前，不得向同一输入框上传下一帖。
- 计划阶段只允许发送一次 `1`；页面恢复时先识别阶段，不能重复确认。
- 必须先取得本轮文案并保存 TXT，再执行最终下载与打包。
- 完整成品必须包含图片、非空 TXT、`GPT作品记录.json` 和真实成品目录。
- 完成后才把素材移动到下一使用次数目录；失败素材留在原位。
- 网页出现 1–3 张低图数、Python/脚本拼图、重试、限额或验证信号时停止当前批次，不继续喂素材。

### 模式切换硬规则

- 停止按钮必须清零 `gptAutoRunning = false`，否则模式切换被 guard 拦截。
- 模式切换 guard 检查 `gptAutoRunning`，不检查 `gptAutoPaused`。
- 暂停后可以切换模式（暂停不算运行中）。
- semi-auto 保留兼容但不在默认下拉框。

## 维护结构改造路线

当前不做一次性重写，按以下顺序逐模块迁移并保持 API 兼容：

1. `public/app.js`：先拆账号窗口与额度、生产状态机、素材/模板树、全局助手、生产历史五个模块。
2. `server.js`：按目录扫描、GPT 工作包、生产记录、备份、分发拆成路由与服务层。
3. 扩展 `sidebar.js`：拆 DOM 状态识别、上传/发送、图片下载、文案提取、工作台桥接。
4. 每迁移一个模块，先保留旧导出适配层，自动测试与真实桌面复验通过后再删旧实现。

结构优化验收指标：

- 页面切换不触发 GPT reload；素材树只懒加载展开内容。
- 单一事件只注册一次监听器，定时器和 `ResizeObserver` 可追踪、可销毁。
- 状态机和 DOM 识别可独立测试，不依赖整份 9 千行脚本。
- 源扩展与内嵌副本具有自动哈希一致性检查。

## 工作流拆解方法论（2026-08-03）

> 核心思想：把任何复杂流程拆成一个个独立的小模块，每个模块只做一件事，模块之间通过顺序排列组合。这是第一性原理在工程中的具体用法——追溯每个动作的本源，把它拆到不可再分的最小单元。

### 为什么要拆

- 泛泛描述（"帮我做个自动生产流程"）无法精准定位卡点；拆成小模块后，每个模块都能独立测试、独立排错。
- 类似 RPA、N8N 的思路：每个节点是一个原子操作，通过拖拽排列组合成完整工作流。
- 模块复用：同一个"随机等待"模块可以用在任意环节，不需要每个环节各写一套。

### 拆解原则

1. **一个模块只做一件事**：检测是检测，等待是等待，发送是发送。不要把"检测+等待+发送"揉进一个模块。
2. **模块可独立测试**：每个模块有明确的输入条件和输出结果，可以单独验证。
3. **模块可自由组合**：用户通过拖拽排列模块顺序，系统按顺序执行。模块之间不硬编码依赖。
4. **主流程模块 vs 工具模块**：主流程模块（上传、等待计划、发送确认等）由状态机驱动；工具模块（随机等待、时间窗口、检测、失败重试）在主流程节点之间自动插入执行。
5. **检测和等待分离**：检测是瞬间动作（检测到=通过，未检测到=报告），等待是时间模块（固定等待/随机等待）。用户通过组合"检测+随机等待"实现"检测到后等一会儿再继续"的效果。

### 模块分类

| 分类 | 图标 | 说明 | 模块示例 |
|------|------|------|----------|
| 执行 | ▶ | 产生实际动作的模块 | 上传帖子、发送文字、下载图片、保存文案、移动归档 |
| 等待 | ⏳ | 等待某条件满足或时间流逝 | 等待计划、等待图片、等待文案、固定等待、随机等待 |
| 时间 | 🕐 | 控制执行时间范围 | 时间窗口（开始/结束）、每日定时循环 |
| 流程 | 🔀 | 控制流程走向 | 失败重试 |

### 工具模块执行机制

工具模块（非主流程模块）通过 `executeUtilityStepsBefore(beforeAction)` 函数在主流程关键节点之前自动执行：

1. 函数接收一个主流程动作名作为参数。
2. 按工作流顺序遍历所有已启用模块，执行排在 `beforeAction` 之前的所有工具模块。
3. 使用 `executedUtilityIndices` Set 去重，避免同一工具模块被多次执行。
4. 返回 `false` 表示时间窗口外应暂停；返回 `true` 表示正常继续。

当前已插入调用的4个关键节点：
- `upload-material` 之前：执行时间窗口检查、随机等待等
- `send-confirm` 之前：执行检测计划完成、随机等待等
- `request-copy` 之前：执行检测图片已生成、随机等待等
- `download-images` 之前：执行检测文案已生成、随机等待等

### 默认值原则

- 所有能自动检测的模块默认 `autoDetect: true`
- 等待模块之间默认插入 `wait-random`（1-5秒随机等待），模拟人工操作节奏
- 超时时间仅作为上限，自动检测开启时检测到完成就继续

### 未来项目设计如何应用

设计任何新项目或新工作流时，先按以下步骤拆解：

1. **列出所有动作**：把流程中每个需要执行的操作都列出来，不管大小。
2. **归类**：每个动作归入执行/等待/时间/流程中的一个。
3. **去重**：合并功能重复的动作（如"复制文案"和"保存文案"如果做的是同一件事就合并）。
4. **定义属性**：每个模块定义是否需要文字输入、是否需要超时、是否支持自动检测。
5. **设定默认值**：所有能自动检测的默认开启，等待时间默认短随机（1-5秒）。
6. **确定执行节点**：在主流程中确定哪些节点需要插入工具模块执行点。
7. **验证闭环**：逐个模块验证是否能独立执行，再验证组合后是否能跑通完整流程。
