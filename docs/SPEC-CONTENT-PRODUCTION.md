# 内容制作自动化系统设计说明书

**版本：V1.0，日期：2026-08-04**

> 本文档是内容制作工作台的统一设计依据，覆盖目标、状态机、检测规则、6 种生产模式、限额策略、检查点、成品标准和开发顺序。后续开发与回归测试均以本文档为准。

## 1. 项目目标与背景

### 1.1 目标

构建一个本地内容制作工作台，把"选素材 → 上传 GPT → 等计划 → 发确认 → 等图片 → 求文案 → 打包归档"这条链路从纯人工升级为可控、可恢复、可回归的自动化系统。

核心交付物：

- 一份图片 + 一份非空 TXT + 一份 `GPT作品记录.json`，统一打包到成品库。
- 素材使用次数自动累加并归档到数字目录。
- 支持从单帖人工控制到多账号全自动的 6 种生产模式。
- 跨重启、断网、合盖、唤醒均可从检查点恢复。

### 1.2 背景

- 依赖 ChatGPT 网页端的图像生成能力，通过本地 Electron 工作台内嵌原生 `WebContentsView` 驱动。
- 不调用 OpenAI API，所有交互通过 DOM 检测与桥接扩展完成。
- 平台额度、网页结构、登录态均不可控，必须以网页真实信号为准。

## 3. 核心设计原则

### 3.1 模式只是预设，不是独立代码分支

6 种生产模式共享同一套状态机、同一套检测规则、同一套工作流模块。模式之间的差异只体现在：

- 触发方式（人工/选材/自动选材/定时/轮换/巡检）。
- 素材补充策略（不补充/按次数选/触顶切换/巡检发现）。
- 时间窗口限制（无/07:00-02:00）。

禁止为某个模式单独写一条独立链路。

### 3.2 暂停不是模式

暂停（`gptAutoPaused`）和运行（`gptAutoRunning`）是运行态标志，不是模式。模式切换 guard 检查 `gptAutoRunning`，不检查 `gptAutoPaused`。暂停后可以切换模式。

### 3.3 一帖一帖串行

单个账号窗口同一时刻只处理一个帖子。当前帖子未完成、未失败跳过、未真实限额暂停前，不得向同一输入框上传下一帖。父合集只是批量选取入口，不能把多个帖子合并为一次上传。

### 3.4 成品校验成功才增加使用次数

只有在以下条件全部满足时，才更新素材使用次数并移动素材到数字归档目录：

- 图片数量 = 本批预期数量。
- TXT 非空且文案长度达标。
- `GPT作品记录.json` 已写入。
- 成品目录真实存在。
- 校验全部通过。

失败素材留在原位置，不伪造完成，不归档。

## 4. 内容制作界面布局

### 4.1 左右双栏

```
┌─────────────────────────────────────────────────────────┐
│  顶部账号窗口标签栏（account-1 / account-2 / ...）        │
├──────────────────────┬──────────────────────────────────┤
│  左素材区             │  右 GPT 网页区                    │
│                      │                                  │
│  - 素材树（多选）      │  - 原生 WebContentsView          │
│  - 模板树（多选）      │  - 底部地址栏（前进/后退/访问）     │
│  - 模式选择器          │  - 小猫助手浮层（状态/对话）        │
│  - 开始/暂停/停止按钮   │  - 状态气泡（当前阶段/百分比）      │
│  - 队列列表            │                                  │
│  - 生产记录            │                                  │
└──────────────────────┴──────────────────────────────────┘
```

### 4.2 左素材区职责

- 素材树支持父目录三态选择、多选、懒加载。
- 模板树支持文件夹模板与链接模板双模式。
- 模式选择器下方有动态提示行（`gptModeHint`）和 `?` 说明按钮。
- 队列列表显示当前批次任务、阶段、进度。
- 生产记录可反查成品路径与原素材路径。

### 4.3 右 GPT 网页区职责

- 内嵌原生 `WebContentsView`，默认加载 ChatGPT。
- 底部地址栏可访问普通 `http/https` 网页，返回首页回到 ChatGPT。
- 小猫助手、状态气泡、对话框属于统一通知层，必须覆盖 GPT 网页。
- GPT 网页不能遮挡或压低通知层。

### 4.4 层级硬规则

- 打开小猫对话前先 `await gptWorkbench.hide()`，再显示 DOM 对话框。
- 对话期间 `assistantChatOpen` 锁定原生浮层为隐藏。
- 设置面板、系统对话框、图片大图、历史面板、右键菜单打开时均不显示原生 GPT 视图。
- 切换到非 GPT 标签页时延迟回调不得把 GPT 视图显示到其他页面。

## 5. 统一生产状态机

### 5.1 主状态枚举

```
IDLE                 → 待处理
MATERIAL_SELECTED    → 已选择素材
SESSION_PREPARING    → 准备模板会话
UPLOADING            → 正在上传附件
ATTACHMENTS_READY    → 附件上传完成
PROMPT_READY         → 提示词已填写
SENDING              → 正在发送
WAITING_PLAN         → 等待出图计划
PLAN_READY           → 出图计划已稳定
CONFIRMING           → 发送确认指令
WAITING_IMAGES       → 等待生成图片
IMAGES_READY         → 本批图片已完成
REQUESTING_COPY      → 发送文案提示词
WAITING_COPY         → 等待小红书文案
COPY_READY           → 文案已完成
SAVING_COPY          → 保存TXT
DOWNLOADING          → 下载图片
PACKAGING            → 整理工作包
VALIDATING           → 校验成品
ARCHIVING            → 更新使用次数并移动素材
COMPLETED            → 任务完成
```

### 5.2 异常状态枚举

```
NETWORK_RETRY        → 网络异常，等待重试
PAGE_RECOVERY        → 页面状态恢复中
QUOTA_PAUSED         → 账号触发限额
LOW_OUTPUT           → 图片数量过少
DEGRADED_OUTPUT      → 出现脚本、Python、拼接等降级结果
HUMAN_REQUIRED       → 需要人工判断
FAILED               → 任务失败
SKIPPED              → 任务已跳过
```

### 5.3 关键约束

- 确认指令只发一次：`checkpoint.confirm_sent_at != null` 时跳过 CONFIRMING，直接进入 WAITING_IMAGES。
- 附件未完成禁止发送：`state != ATTACHMENTS_READY` 时禁止进入 SENDING。
- 文案是下载打包的硬前置：`state != COPY_READY` 时禁止进入 DOWNLOADING。
- 校验通过才能归档：`validationResult.failed.length > 0` 时转 HUMAN_REQUIRED。
- 低图数（1-3 张）不请求文案、不打包、不归档，进入限额恢复等待。

## 6. 页面检测机制

### 6.1 检测原则

状态检测不能只依赖单个关键词或单一 DOM 元素，必须使用多信号综合判断。核心信号源：

1. 发送按钮状态（图标 + 可用性）。
2. 消息流变化（DOM 增量 + 文本稳定性）。
3. 附件卡片状态。
4. 图片节点与文件卡片。
5. 文本内容特征匹配。

### 6.2 发送按钮检测

- `stopButton` 可见 → GPT 仍在生成。
- `sendButton` 可用 → 可以提交。
- `sendButton` 禁用 → 附件或文本未就绪。
- 均不可见 → 页面异常。

发送按钮只能作为辅助信号，不能单独决定状态。

### 6.3 消息流检测

消息内容连续稳定 8 秒 + `stopButton` 消失 + 页面没有新增 DOM 节点 = 可以进入下一状态。

### 6.4 附件上传检测

必须全部确认：原生附件卡片已出现、卡片数量 = 任务素材数量、无上传中状态、TXT 附件已出现、发送按钮可用、输入框提示词完整。

`实际附件数 < 预期附件数` 且等待超时后返回 `UPLOAD_LIMIT_SIGNAL`，错误中包含 `实际/预期`。

### 6.5 出图计划检测

识别关键词：`出图计划`、`P1…Pn`、`共X页`、`先生成前10张` 等。

页数解析优先级：`P1...Pn` 标记 → 明确页码标题 → `共X页` → `先生成前N张` → 默认 10 张标记待核对。

**总计划 vs 本批预期**：总计划 = 12 页、本批预期 = 10 页时，本批预期 = 10，不要求 12。此规则不可回退。

### 6.6 确认指令检测

计划稳定后 1-5 秒内只发送一次确认文字，默认 `1`。计划未完成不得发送。页面恢复时先识别阶段，不能重复确认。

### 6.7 图片生成检测

- 绑定本轮助手回复，不能全页混入旧回复。
- 优先以原生"复制回复"动作确认整条回复完成。
- 沙盒文件按钮 `P1…Pn` 必须从当前回复外层 `conversation-turn` 读取。
- 同一文件的不同签名 URL 按 `backend-api/estuary/content?id=file_*` 的 `id` 归一化去重。
- 缩略图（48×48）允许计数，不能用通用尺寸过滤漏计。

### 6.8 文案检测

完成条件：最新回复属于当前文案请求、没有继续生成、文本长度 ≥ 300（推荐 ≥ 600）、包含正文、文本稳定若干秒。

### 6.9 错误与降级检测

| 错误类型 | 检测特征 | 处理 |
|---------|---------|------|
| 网络错误 | `network error`、`Something went wrong`、重试按钮 | NETWORK_RETRY |
| 限额提示 | `You've reached...`、rate limit 文案 | QUOTA_PAUSED |
| 验证码 | CAPTCHA / 人机验证元素 | HUMAN_REQUIRED |
| 图片生成失败 | `Something went wrong while generating your image` | 重试 1 次 → 人工 |
| 内容安全拦截 | `content policy`、`safety` | HUMAN_REQUIRED |
| Python 代码 | ` ```python ` 标记 | DEGRADED_OUTPUT |
| 脚本拼图 | script 标签、拼接特征 | DEGRADED_OUTPUT |
| 仅教程无图 | 解释文字多但无图片节点 | DEGRADED_OUTPUT |
| 低图数 | 图片 1-3 张 + 已停止 + 计划 > 3 | LOW_OUTPUT |

降级处理：停止当前任务、不当作成品、不增加使用次数、记录页面证据、转 HUMAN_REQUIRED 或重试队列。

## 7. 基础工作流模块

### 7.1 模块分类（7 大类）

| 分类 | 图标 | 说明 | 模块示例 |
|------|------|------|----------|
| 触发 | ⚡ | 启动生产链路的入口 | 人工点击、选材后启动、定时窗口、触顶切换、巡检发现 |
| 素材 | 📦 | 素材选择与占用 | 勾选帖子、父合集拆帖、按次数选材、占用锁、归档 |
| 会话 | 💬 | GPT 会话管理 | 创建新聊天、复用当前会话、链接模板续接、母版注入 |
| 页面交互 | 🖱 | 与 GPT 网页的交互 | 上传附件、填写提示词、点击发送、清理草稿 |
| 检测 | 🔍 | DOM 状态识别 | 发送按钮、消息流稳定、附件就绪、计划完成、图片完成、文案完成、错误降级 |
| 控制 | 🎛 | 流程走向与等待 | 等待计划、等待图片、等待文案、固定等待、随机等待、失败重试、时间窗口 |
| 输出 | 📤 | 成品落地 | 下载图片、保存 TXT、查重打包、校验成品、写记录 |

### 7.2 模块执行机制

- 主流程模块由状态机驱动。
- 工具模块（随机等待、时间窗口、检测、失败重试）通过 `executeUtilityStepsBefore(beforeAction)` 在主流程关键节点之前自动执行。
- 关键节点：`upload-material`、`send-confirm`、`request-copy`、`download-images` 之前。
- 使用 `executedUtilityIndices` Set 去重，避免同一工具模块被多次执行。

### 7.3 默认值原则

- 所有能自动检测的模块默认 `autoDetect: true`。
- 等待模块之间默认插入 `wait-random`（1-5 秒随机等待），模拟人工操作节奏。
- 超时时间仅作为上限，自动检测开启时检测到完成就继续。

## 8. 6 种生产模式定义

> 模式名称必须严格使用下表的 key 与中文名，不得混用旧称。

| key | 中文名 | 说明 |
|---|---|---|
| manual | 人工控制 | 用户全手动，软件只上传附件到输入框 |
| automatic | 选材后自动 | 用户选材后全自动闭环，不补充新素材 |
| single | 单账号全自动 | 自动选材 + 永不停歇 + 触顶探测 |
| scheduled | 定时单账号全自动 | 单账号全自动 + 定时窗口（07:00-02:00） |
| rotate | 多账号全自动 | 多账号轮换 + 触顶切换 |
| patrol | 单账号多对话巡检 | 历史对话巡检（实验模式，默认关闭） |

### 8.1 manual（人工控制）

- **用户负责**：选择帖子、填写提示词、点击发送、发送 `1`、请求文案、下载打包。
- **软件负责**：把所选帖子的附件上传到输入框；不自动点击发送。
- **关键规则**：上传后发送按钮禁用并显示"等待手动发送"；手动下载前必须已有文案；手动打包不会产生缺 TXT 半成品。
- **素材优先级**：不适用，用户全权选择。
- **开发阶段**：阶段一。

### 8.2 automatic（选材后自动）

- **用户负责**：勾选一个或多个帖子（或父合集），点击开始。
- **软件负责**：逐帖自动完成 上传 → 等计划 → 发 1 → 等图 → 求文案 → 打包归档。
- **关键规则**：严格逐帖串行；当前帖子未结束前不上传下一帖；计划后只发送一次 `1`；图片与 TXT 统一打包；成功后才增加使用次数；失败素材留在原位置；队列跑完即停，不自动补充新素材；触顶恢复只续剩余队列。
- **素材优先级**：不适用，按用户勾选顺序。
- **开发阶段**：阶段二。

### 8.3 single（单账号全自动）

- **用户负责**：点击开始，后续无需干预。
- **软件负责**：自动选材 + 永不停歇循环 + 触顶探测与恢复。
- **关键规则**：优先处理用户已勾选的帖子；勾选队列处理完后从全素材库选材；按使用次数从低到高选择；触顶后暂停并记录下次探测时间；到探测时间后自动恢复；恢复后只续剩余队列，不补充新素材；跨重启从检查点续跑；工作时段外不领取新任务。
- **素材优先级**：勾选队列优先 → 全素材库按使用次数升序 → 同次数按素材名排序。
- **开发阶段**：阶段三。

### 8.4 scheduled（定时单账号全自动）

- **用户负责**：配置工作时段（默认 07:00-02:00），点击开始。
- **软件负责**：工作时段内按 single 模式运行；非工作时段不领取新任务。
- **关键规则**：工作时段内（07:00-02:00）自动生产；非工作时段不领取新任务；当前帖子允许安全完成；软件启动后自动检查是否可继续；联网恢复后自动继续；电脑唤醒后自动继续。
- **素材优先级**：同 single。
- **开发阶段**：阶段四。

### 8.5 rotate（多账号全自动）

- **用户负责**：配置多个账号窗口，点击开始。
- **软件负责**：每个账号窗口独立运行 single 模式；触顶切换到下一个可用账号。
- **关键规则**：每个账号一次只领取一个帖子；账号 A 触顶只暂停账号 A；账号 B、C 继续运行；禁止把账号 A 素材注入账号 B；切换可见窗口不影响任务绑定；所有账号共享素材占用锁；成功不是轮换条件，真实网页信号才是轮换条件。
- **素材优先级**：各账号独立选材，共享占用锁。
- **开发阶段**：阶段五。

### 8.6 patrol（单账号多对话巡检）【实验】

- **用户负责**：开启实验开关，选择巡检账号。
- **软件负责**：遍历账号历史对话，按对话状态补齐未完成的步骤。
- **关键规则**：识别对话有出图计划 → 发 1；识别对话有完整图片 → 求文案；识别对话有完整文案 → 下载归档 + 上传新素材；识别对话只有 1-3 张图 → 限额处理；识别对话空白 → 标记不可识别；巡检完成后循环。默认关闭，不自动启动。
- **素材优先级**：不主动选材，按对话状态补齐。
- **开发阶段**：阶段六。

### 8.7 兼容保留

- `semi-auto` 保留兼容但不在默认下拉框。
- `normalizeGptProductionMode` 支持新旧别名映射。
- `isContinuousGptMode` 将 `single`、`scheduled`、`rotate`、`patrol` 判定为连续模式。

## 9. 低图数、限额和重试策略

### 9.1 不硬编码官方额度

不要把"每 3 小时 50 张"当作绝对规则写死。系统应记录实际页面信号和真实时间。

### 9.2 关键时间字段

```json
{
    "confirm_sent_at": "发送确认指令1的时间",
    "image_generation_detected_at": "首次检测到图片开始生成的时间",
    "first_image_ready_at": "第一张图完成时间",
    "last_image_ready_at": "最后一张图完成时间",
    "quota_detected_at": "检测到真实限额的时间",
    "next_probe_at": "下次允许探测时间"
}
```

### 9.3 额度周期计算

- 优先方案：`next_probe_at = image_generation_detected_at + 3 小时`。
- 退化方案：无法检测到图片开始生成时间时，`next_probe_at = confirm_sent_at + 3 小时`。
- 探测失败后随机 10-20 分钟自动重试。

### 9.4 低图数判定

必须同时满足：计划预期图片数 > 3、GPT 已经停止生成、最新回复稳定、实际可下载图片数量 = 1-3、没有继续生成迹象。

判定后处理：标记 LOW_OUTPUT、保存已生成图片作为诊断证据、不打包正式成品、不增加使用次数、暂停当前账号、按 `image_generation_detected_at + 3 小时` 计算下次探测时间。

### 9.5 网络异常退避策略

```
第1次重试：等待 2 分钟
第2次重试：等待 5 分钟
第3次重试：等待 10 分钟
最多 3 次
```

每次重试前检查：页面是否恢复、当前任务阶段、是否已经发送成功、是否已经出现计划或图片。

禁止行为：盲目重新上传、在网络异常时继续发送提示词、将网络错误与额度触顶混为一类。

### 9.6 页面检测不确定

每 10 分钟重新检查一次，最多检查 2 次，仍然无法判断转 HUMAN_REQUIRED。

### 9.7 恢复后重试提示词

额度恢复后重试请求文案：

```
请重新批量生成刚才这套图片。刚才生成数量不足或发生错误，请严格按照已经确认的出图计划完整生成本批作品，不要解释，不要输出脚本或Python代码。
```

恢复后仍只有 1-3 张：再确认一次页面没有继续生成、标记当前任务需要人工检查、不无限重复、可跳过该素材、继续下一条素材或停止当前账号。

### 9.8 出图失败重试检测

检测特征：`something went wrong`、`sorry about that`、`network error`、`connection timeout`、`please try again`。

执行流程：发送确认指令 1 → 等待 6 秒 → 读取最新助手消息 → 匹配错误模式 → 未重试过则随机等待 120-300 秒后重新发送 `1` → 标记 `confirmRetried = true` → 再次检测：成功继续、失败转人工。单个提示词最多重试 1 次。

## 10. 工作流组合器

### 10.1 设计思想

把复杂流程拆成独立小模块，每个模块只做一件事，模块之间通过顺序排列组合。类似 RPA、N8N 的思路：每个节点是一个原子操作，通过拖拽排列组合成完整工作流。

### 10.2 拆解原则

1. 一个模块只做一件事：检测是检测，等待是等待，发送是发送。
2. 模块可独立测试：每个模块有明确的输入条件和输出结果。
3. 模块可自由组合：用户通过拖拽排列模块顺序，系统按顺序执行。模块之间不硬编码依赖。
4. 主流程模块 vs 工具模块：主流程模块由状态机驱动；工具模块在主流程节点之间自动插入执行。
5. 检测和等待分离：检测是瞬间动作，等待是时间模块。

### 10.3 动作类型

上传素材、等待计划、发送文字、等待图片、下载本轮、请求文案、等待文案、复制 TXT、查重打包、归档、结束/跳过。

### 10.4 安全依赖

- 不得把"发送 1"放到计划完成前。
- 不得在图片和文案校验前打包。
- 界面拖动到无效顺序时直接提示原因，不保存假流程。

### 10.5 任务冻结

点击开始生产时，把当时的流程保存为本批快照；运行期间修改只作用于下一批，不得改变当前任务。

## 11. 任务检查点与断点恢复

### 11.1 检查点写入时机

每个主状态进入时立即写检查点。检查点字段清单：

| 状态 | 检查点新增字段 |
|------|-------------|
| MATERIAL_SELECTED | taskId, materialPath, materialHash |
| SESSION_PREPARING | templateId, sessionUrl, accountWindowId |
| ATTACHMENTS_READY | attachmentCount |
| SENDING | promptHash |
| PLAN_READY | planText, totalPlannedPages, batchExpectedPages |
| CONFIRMING | confirm_sent_at |
| IMAGES_READY | detectedImageCount, firstImageReadyAt, lastImageReadyAt |
| COPY_READY | copyText, txtTempPath |
| DOWNLOADING | imageDownloadDir |
| PACKAGING | outputDir |
| ARCHIVING | usageUpdated |
| QUOTA_PAUSED | quota_detected_at, next_probe_at |

### 11.2 完整检查点字段清单

```
taskId                 → 任务唯一标识
materialPath           → 素材帖子目录绝对路径
materialHash           → 素材内容哈希
templateId             → 模板标识
sessionUrl             → GPT 会话 URL
accountWindowId        → 账号窗口档案 ID
attachmentCount        → 附件数量
promptHash             → 提示词哈希
planText               → 计划正文
totalPlannedPages      → 总计划页数
batchExpectedPages     → 本批预期页数
confirm_sent_at        → 确认指令发送时间
detectedImageCount     → 检测到的图片数
firstImageReadyAt      → 首图完成时间
lastImageReadyAt       → 末图完成时间
image_generation_detected_at → 图片开始生成时间
copyText               → 文案正文
txtTempPath            → TXT 暂存路径
imageDownloadDir       → 图片下载目录
outputDir              → 成品输出目录
usageUpdated           → 使用次数是否已更新
quota_detected_at      → 限额检测时间
next_probe_at          → 下次探测时间
runId                  → 本轮运行标识
currentPhase           → 当前阶段
sourceMaterialPath     → 原素材路径
sourceMaterialName     → 原素材名称
sourceMaterialArchivePath → 素材归档后路径
```

### 11.3 状态恢复流程

```
软件重启 / 断网恢复 / 浏览器恢复后：
1. 读取本地检查点文件
2. 检查真实 GPT 页面状态
3. 对比本地记录与页面状态
4. 确定当前真实状态
5. 从下一个安全动作继续
```

### 11.4 恢复禁止行为

- 从头重跑。
- 重复发送提示词。
- 重复发送确认指令。
- 在输入框有残留时继续上传。

### 11.5 跨重启恢复要点

- 每个账号窗口独立保存运行状态、当前阶段、上传确认数和生图数。
- 切换窗口不重置另一窗口的检查点。
- 暂停/继续与停止/启动语义分开：暂停保留当前阶段，停止禁止自动上传和自动重试但保留队列与登录分区。
- 首次额度探测按本轮第一次真实消耗起点计算。

## 12. 成品打包标准

### 12.1 成品目录结构

```
成品库根目录/
└── 20260802_155923_帖子标题/
    ├── P1.png
    ├── P2.png
    ├── ...
    ├── P10.png
    ├── 帖标题.txt              ← 非空文案 TXT
    └── GPT作品记录.json         ← 批次元数据
```

### 12.2 校验项目

成品目录必须真实存在，并满足以下全部条件才允许归档：

- 图片数量 = 本批预期数量（`batchExpectedPages`）。
- 所有图片可解码且 SHA-256 不等于源图。
- TXT 文件存在且非空，文案可见字符 ≥ 300（推荐 ≥ 600）。
- `GPT作品记录.json` 已写入，包含 `sourceMaterialPath`、`sourceMaterialName`、`sourceMaterialArchivePath`、`packagePath`、批次号、各阶段耗时。
- 工作包批次数与磁盘图片数一致。
- 历史接口返回 `packageValid=true`、`packageExpectedImageCount`、`packageValidatedByRecord=true`。

### 12.3 打包入口统一

手动"下载并打包"与自动打包共用 `packageDownloadedReply`；服务端按批次号从 UTF-8 `GPT作品记录.json` 恢复权威成品路径。文案或图片不完整时二者都不允许报成功。

### 12.4 失败处理

缺 TXT、图片不足、下载不完整或成品目录不存在时：不归档素材、不显示成功、不增加使用次数、失败素材留在原位置、历史记录显示"待核对"。

## 13. 素材使用次数系统

### 13.1 目录命名规则

- 新归档只允许写入素材库根目录下的纯数字目录：`1`、`2`、`3`、`4`……，数字就是该帖子成功使用次数。
- `0` 次素材不额外建立数字目录；未使用素材继续留在原分类目录或用户手动目录中。
- `已使用一次`、`已上传 2 次`、`已制作三次GPT` 等历史目录继续兼容识别，但不再新建。

### 13.2 次数计算

- 归档前先取元数据账本次数与物理路径次数的较大值再加一，避免旧账本为 0 时把 `1` 次素材错误留在 `1`。
- 数字目录只读取素材库根目录的第一层，帖子标题中的日期或数字不会被误认为使用次数。

### 13.3 增加次数的硬前置

只有在第 12 章成品校验全部通过后，才执行归档：更新使用次数、移动素材到数字目录、写回 `sourceMaterialArchivePath`。

### 13.4 失败素材处理

失败素材留在原位置，不归档、不增加次数、不伪造完成记录。

## 14. 开发顺序（6 阶段）

### 阶段一：稳定人工控制（manual）

- 上传附件到输入框，不自动发送。
- 手动发送、文案、下载、打包链路打通。
- 手动打包不产生缺 TXT 半成品。

### 阶段二：选材后自动（automatic）

- 单帖完整闭环。
- 父合集拆帖严格串行。
- 断点恢复。
- 队列跑完即停，不补充新素材。

### 阶段三：单账号全自动（single）

- 自动选材（勾选队列优先 + 全素材库按次数升序）。
- 永续队列。
- 触顶探测与恢复。
- 跨重启从检查点续跑。

### 阶段四：定时单账号全自动（scheduled）

- 时间窗口（默认 07:00-02:00）。
- 开机/唤醒/联网恢复。
- 非工作时段不领取新任务。

### 阶段五：多账号全自动（rotate）

- 独立 worker + 独立额度。
- 素材占用锁。
- 触顶切换到下一个可用账号。
- 真实双账号验收。

### 阶段六：单账号多对话巡检（patrol）

- 实验模式，默认关闭。
- 历史对话状态识别与补齐。
- 巡检循环。
