# 分发功能与作品集状态设计

日期：2026-07-24
状态：用户已批准，0.2.0 第一阶段已实现

## 1. 目标

把现有“手机分发”升级为覆盖手机补货、公众号领取、分发历史和归档记录的“分发功能”；同时让“作品集”能够按内容类型和平台资格筛选，并查看每套合集的真实可用状态。

界面必须同时支持：

- 用户通过按钮、筛选和菜单手动完成全部操作；
- Codex 通过同一动作接口代用户操作；
- 两种模式共用同一套资格判断、日志和安全规则。

## 2. 已确认的业务规则

### 2.1 内容类型

- 文件夹名称含 `[泛]`：游戏/泛流量。
- 文件夹名称含 `[转]`：团建转化。
- 不含合法类型标签：未分类，不进入自动随机分发候选。
- 隐藏、空、断链、非 Junction 或目标不一致的项目不进入可用库存。

### 2.2 手机分发资格

- 双平台手机只能使用小红书与抖音两个活跃 Junction 同时存在、指向同一源合集的项目。
- 5号苹果6和8号红米9A（A10）只使用小红书。
- 单平台手机接收成功后，删除对应小红书 Junction，并把同合集剩余抖音 Junction 移入 `发布空间/归档/抖音`。
- 任何清理或归档都只能在接收确认后执行，且不能删除源合集。

### 2.3 公众号

- 公众号由电脑批量上传，不向手机发送。
- 领取后状态为“已领取待上传”，不能显示成“已发布”。
- 只有用户手动确认电脑上传完成，状态才变成“公众号已使用”。
- 上传失败时可依据领取日志恢复公众号 Junction。

## 3. 状态来源与标签原则

界面标签采用实时计算，不修改合集名称，不另建一套需要人工维护的标签数据库。

| 状态 | 唯一判断来源 |
|---|---|
| 游戏/泛流量、团建转化 | 合集名称中的 `[泛]`、`[转]` |
| 小红书可用 | 小红书活跃 Junction 存在且有效 |
| 抖音可用 | 抖音活跃 Junction 存在且有效 |
| 双平台可分发 | 小红书、抖音 Junction 同时存在并指向同一源合集 |
| 抖音已归档 | `归档/抖音` 中存在有效 Junction |
| 公众号可领取 | 公众号活跃 Junction 存在且有效 |
| 已领取待上传 | `official-account-usage-log.csv` 的最新状态 |
| 手机分发历史 | `device-usage-log.csv` |
| 公众号已使用 | 用户手动确认后写入公众号使用日志 |

Skill 和工作台之间增加结构化状态输出，但不复制传输、Junction 删除或归档逻辑。

## 4. 信息架构

### 4.1 左侧导航

- “手机分发”改名为“分发功能”。
- 保持现有六个入口，不新增独立库存或归档页面。

### 4.2 作品集

作品集负责回答：

- 一共有多少套合集；
- 哪些属于游戏/泛流量，哪些属于团建转化；
- 哪些平台仍可使用；
- 哪些合集可用于双平台手机；
- 每套合集的具体内容和历史。

顶部第一层类型筛选：

`全部｜游戏/泛流量｜团建转化｜未分类`

第二层平台状态筛选：

`双平台可用｜小红书可用｜抖音已归档｜公众号可用｜已领取待上传｜全部已使用`

删除“缺页待续接”。缺页属于素材生产，不属于合集库存。

合集卡片显示：

- 合集名称与内容类型；
- 当前条数，如 `14/14`、`9/14`；
- 小红书、抖音、公众号状态标签；
- 双平台资格；
- 异常提示；
- “查看详情”按钮。

详情抽屉显示：

- 源目录、条数、文件数、容量；
- 三个平台当前状态；
- 双平台资格和排除原因；
- 手机分发记录；
- 公众号领取与确认记录；
- 已删除或归档的平台入口；
- 打开源文件夹、进入分发等手动操作。

### 4.3 分发功能

顶部切换：

`手机补货｜公众号领取｜分发记录｜归档记录`

#### 手机补货

- 显示已登记设备总数、当前在线、需要补货、传送中；
- 支持按公司/个人、在线/离线、库存状态筛选；
- 设备卡提供“随机补货”“选择作品集”“查看详情”；
- 随机补货可选泛流量、团建转化或默认泛流量；
- 传送中显示文件数、容量、进度、速度和取消；
- 完成后显示作品数前后变化、删除与归档结果；
- 失败时明确显示“未清理任何平台入口”。

#### 公众号领取

- 显示公众号可领取库存；
- 默认优先选择小红书和抖音入口均已使用的合集；
- 支持“给江湖有旅人团建策划师拿一个公众号作品”；
- 领取后显示源文件夹和“已领取待上传”；
- 提供“确认上传完成”和“上传失败，恢复入口”两个手动动作。

#### 分发记录

- 按设备、内容类型、平台和日期筛选；
- 显示发送目标、合集、传输协议、接收确认、作品数变化和入口处理结果；
- 不把“打开分享”或“领取”冒充发布成功。

#### 归档记录

- 显示归档平台、合集、原因、时间和来源设备；
- 仅提供经过校验的“恢复入口”动作；
- 恢复时禁止覆盖已经存在的活跃入口。

## 5. Codex 双模式

每个页面保留完整手动按钮。Codex 操作条只提供另一种入口，例如：

- “给5号补一个泛流量”
- “筛出双平台都没用过的团建转化合集”
- “给江湖有旅人团建策划师拿一个公众号作品”
- “确认刚才公众号已经上传完成”

Codex 必须调用与界面按钮相同的动作接口，不直接绕过资格检查或安全校验。

## 6. 结构化状态接口

工作台需要从现有 Skill 获得至少以下字段：

```json
{
  "collection": "作品集_038[转]",
  "type": "conversion",
  "itemCount": 14,
  "sourceValid": true,
  "xhs": "available",
  "douyin": "available",
  "officialAccount": "available",
  "dualPlatformEligible": true,
  "exclusionReasons": [],
  "deviceHistoryCount": 0,
  "officialAccountState": null
}
```

可用状态包括：

- `available`
- `used`
- `archived`
- `reserved_pending_upload`
- `confirmed_published`
- `unknown`
- `invalid`

## 7. 错误与安全反馈

- 入口缺失、断链、源目录为空、目标不一致时停止分发，并说明排除原因。
- 手机接收未确认时不删除、不归档。
- 公众号领取不等于发布完成。
- 恢复 Junction 前验证源目标和目标位置。
- 界面不展示设备唯一标识、网络地址、账号凭据或用户内容正文。
- 所有危险操作显示将影响的平台和可恢复性。

## 8. 方案比较

### 方案A：在合集名称上追加更多标签

优点是资源管理器中直观；缺点是名称会越来越长，且名称、Junction和日志容易冲突。否决。

### 方案B：单独维护一份标签数据库

筛选灵活，但需要处理同步、迁移和数据损坏，现阶段没有必要。暂不采用。

### 方案C：从目录和日志实时计算标签

复用现有唯一真源，不改变源合集，能够反映归档和领取状态。采用。

## 9. 验收标准

- “手机分发”已改名为“分发功能”。
- 作品集不再显示“缺页待续接”。
- `[泛]`、`[转]` 和未分类可以准确筛选。
- 双平台可用数量只统计两个有效同源 Junction 同时存在的合集。
- 点击合集可查看三平台状态和完整历史。
- 公众号领取后显示“已领取待上传”，手动确认后才显示“公众号已使用”。
- 手动按钮与 Codex 指令产生一致结果。
- 任何失败路径都不会清理源合集或错误平台入口。
- 现有 `device-folder-transfer` 的传输和安全逻辑不被复制或重写。
