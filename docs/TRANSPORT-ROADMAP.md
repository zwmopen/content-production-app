# 传输层路线与 P2P / 中继边界

> 记录日期：2026-08-14。本文是设计决策，不表示远程中继或 WebRTC 已经上线。

## 当前真实状态

### 电脑 ↔ 手机主链

- `device-folder-transfer` 使用 UDP `45834` 做局域网发现，收到设备后通过 HTTP `45833` 建立任务并上传文件；文件上传本质是 TCP 字节流。
- 任务顺序是：创建任务 → 按文件上传 → 接收端校验 `X-File-Sha256` → `commit`；失败时取消任务。这个闭环已经是当前默认传输真源。
- 工作台的自动补货仍要求设备已发现、在线、已授权、目标分类库存已知、库存低于阈值且存在未成功发送的 `workId`。不能因为引入新传输方式而放宽这些安全条件。

### 手机端已有的“中转”

- Android 接收端的 `/v2/info` 已报告 `relayVersion/relayEnabled`，并有本地 `relay-queue`、过期时间和 hopLimit。
- 这只是**局域网内手机之间的设备级转发骨架**：收到任务后缓存，再等待下一跳设备；它不提供公网穿透、账号鉴权、云端存储或跨网络可达性。
- 因此当前不能对外宣称“已支持 P2P”或“已支持远程中继”。

## 第一性原理决策

1. 用户要的是可靠地把文件送达设备并可恢复，而不是某个协议名称。
2. 同一 Wi‑Fi、低流量场景下，现有 LAN V2 已经是数据面直连：电脑直接把文件发给手机，不经过云端。换成 WebRTC/P2P 不会自动变快，反而会增加 NAT、权限、后台运行、重试和 iOS 兼容成本。
3. 跨网络场景才需要新的路径。真正的跨网 P2P 必须有信令、NAT 穿透（STUN）和失败后的 TURN/中继；只写一个“P2P 开关”不能解决可达性。
4. 手机兼容必须以能力协商和向后兼容为前提。小米/红米、VIVO、华为共用协议；Apple 需要独立 iOS 接收端和真机验证，不能把 Android 包当成 Apple 兼容。

## 推荐路线

| 层 | 用途 | 当前决定 | 进入条件 |
|---|---|---|---|
| `lan-v2` | 同网手动发送、自动补货 | **默认且继续维护** | 当前协议；不替换 |
| `peer-forward` | 同一局域网内手机临时中转 | **保留现有骨架，暂不扩大范围** | 先完成中转去重、过期、重试和日志回归 |
| `direct-peer` | 未来的可选直连传输（可评估 WebRTC/QUIC） | **设计预留，不立即上线** | 现有 LAN V2 有可量化瓶颈，并完成能力协商、断点、哈希、提交和降级 |
| `relay` | 跨网或直连失败时的远程路径 | **后置、显式开关** | 独立服务、短期令牌、端到端加密、限时缓存、配额和审计 |

## 不应现在做的事

- 不用 WebRTC/P2P 替换现有 LAN V2。
- 不把电脑偷偷变成公网文件中继，也不在没有加密/鉴权/清理策略时上传用户作品到云端。
- 不为了“通用”删除当前的 SHA-256、commit、成功去重、失败恢复和未知库存保护。
- 不在手机端版本未完成跨品牌手动闭环前打开自动中继。

## 以后真正开发时的最小接口

所有传输方式都挂在同一个任务协议下，由电脑端调度：

`discover → negotiate(capabilities/appVersion) → createTask → stream/chunk → sha256 → commit → ledger`

能力字段至少包括：

- `transport`: `lan-v2` / `peer-forward` / `direct-peer` / `relay`
- `protocolVersion`、`appVersion`、`resume`、`maxChunkBytes`
- `inventory`/`workCounts` 是否已知
- `relayAllowed`、`relayExpiresAt`（默认关闭）

任何新传输都必须满足：

- 同一 `taskId` 可安全重试，不产生重复作品；
- 分块/断点后仍以 SHA-256 + `commit` 作为唯一成功条件；
- 新能力协商失败自动回退 `lan-v2`，而不是让任务卡死；
- 传输日志能标明实际路径和失败阶段；
- 旧手机仍能完成手动发送，才能发布新手机包。

## 当前阶段与验收门槛

当前阶段停在“方案与协议边界”，不改变线上传输链路。下一步若启动开发，顺序应为：

1. 记录 LAN V2 的真实基线：发现耗时、传输速率、失败率、断线恢复和大文件表现。
2. 给 `/v2/info` 增加可选能力字段并做旧客户端兼容测试，不启用新路径。
3. 补齐 Android `peer-forward` 的去重、过期、失败恢复和可观测性测试。
4. 只有基线证明 LAN V2 是瓶颈，才做 `direct-peer` 小范围实验；实验失败必须无感回退。
5. 最后再评估独立的远程 relay 服务，并单独做安全、成本、隐私和配额验收。
