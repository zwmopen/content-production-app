# 电脑端 ↔ 手机端兼容矩阵与升级门禁

> 这是图文项目工作台的产品级约束，不是某一次 VIVO 修复的临时说明。任何手机端或自动分发改动都必须遵守本文件。

## 产品边界

- 电脑端是统一控制台：负责设备发现、库存读取、手动发送、自动补货、去重、重试、恢复、日志和配置。
- 手机端是配套接收端：负责在线广播、库存分类上报、接收文件/作品、校验、提交确认和版本信息。
- 两端通过能力协议协作，不按品牌写分支。品牌差异只能进入适配层、能力声明或安装包，不得复制一套“VIVO 逻辑”“小米逻辑”。
- “精准/泛流量”、作品类型、默认目录、平台名称、库存阈值属于项目 profile；发现、库存、传输、校验、去重、重试和恢复属于通用内核。

## 必须保留的设备族

| 设备族 | 当前实现/状态 | 版本门槛 | 真实验收要求 |
| --- | --- | --- | --- |
| 小米 / 红米 Android | 已有接收端与 Wi‑Fi 传输链路 | 使用当前已发布兼容版 | 在线广播、分类库存、手动发送、自动补货、断线重连 |
| VIVO Android | 已发现；0.6.19 候选包待手机安装确认 | `versionCode 57 / 0.6.19` 候选 | 安装后 `/v2/info` 有分类库存，再验手动→自动 |
| 华为 Android | 作为既有登记设备，必须保留协议兼容 | 不得因 Android 升级删除 | 在线、手动发送、库存未知保护、失败重试 |
| Apple iPhone | 目标支持设备族；当前不能把 Android APK 当作 iOS 支持 | 需要独立 iOS 接收端/适配层 | 在没有 iOS 实机验证前不得宣称“已支持” |
| 电脑端工作台 | 当前真源 | 桌面版本与协议版本分离 | 旧登录、生产队列、作品和分发账本不受升级影响 |

## 版本升级门禁

每次手机端升级都必须：

1. 先跑协议/单元测试，再构建 Debug 与 Release 包。
2. 保持 application id、签名链、数据目录和协议字段向后兼容；禁止为修一个品牌清空其他设备数据。
3. 至少用一台 Android 设备做真实手动发送；自动补货必须在“分类库存已知、设备已批准、低于阈值、有候选作品”时才触发。
4. 小米/红米、VIVO、华为分别记录真实结果；未实测的设备标记“待验证”，不能写成“兼容完成”。
5. Apple 只有在 iOS 接收端和实机链路完成后才从“目标支持”改为“已验证”。
6. 先保留旧包和可恢复路径，再发布新包；失败 3 次暂停，设备重新在线后允许再次尝试。

## 手动优先、自动随后

- 新设备、新版本、新分类先通过手动发送证明“发现 → 连接 → 接收 → 提交 → 记录”闭环。
- 手动链路稳定后才开启自动补货；自动模式不得绕过库存未知保护、首次授权、成功去重和失败恢复。
- 自动化只负责减少重复点击，不改变人工可验证的事实边界。
